# The two association documents

**These files are not served from this repository.** Nothing here is published,
and putting either of them on a web path would be a mistake — see
[Where they are actually served](#where-they-are-actually-served) below.

They are the **reviewed record** of what the three shipped apps claim, rendered
from one source of truth in
[`wallet/zuuli/scripts/app-link-association.mjs`](../../../wallet/zuuli/scripts/app-link-association.mjs)
and regenerated by:

```sh
node wallet/zuuli/scripts/app-link-association.mjs --print=assetlinks \
  > docs/intent-bridge/association/assetlinks.json
node wallet/zuuli/scripts/app-link-association.mjs --print=aasa \
  > docs/intent-bridge/association/apple-app-site-association.json
```

The same script re-renders them on every ZUULI `npm test` run and fails if the
committed bytes differ, so the record and these documents cannot drift.

## Why they exist here at all

[`PROTOCOL.md` §7](../PROTOCOL.md#7-what-is-blocked-on-461) refuses to ship the
intent bridge over a custom scheme: any app can register
`cash.free2z.zuuli://`, so a hostile app can impersonate the sender of an intent
and intercept the response. A **verified** App Link / Universal Link is
domain-bound — only the app whose package or team owns the association receives
the URL — and that property is made of two documents plus three client claims.
The client claims live in this repo, next to the apps. The documents are the
other half of the same reviewed decision, so they are written down next to the
claims rather than only in the deployment repository, where nothing can check
them against a manifest.

## The path scheme

```
/oauth/callback     -> cash.free2z.zuuli   (pre-existing, live, unchanged)
/bridge/zuuli/*     -> cash.free2z.zuuli   (intent REQUESTS into the wallet)
/bridge/free2z/*    -> cash.free2z.free2z  (intent RESPONSES back to free2z)
/bridge/e2e2z/*     -> cash.free2z.e2e2z   (intent RESPONSES back to e2e2z)
```

The second segment names the **receiving** app. A URL's only job is to reach the
right process; the bridge's own `caller` field says who sent it, and
[`CALLER-AUTHENTICATION.md` §5](../CALLER-AUTHENTICATION.md#5-what-is-not-built)
is explicit that the claim is not authenticated by the message.

**No two apps may match the same URL.** If they did, the OS would pick between
them arbitrarily and a response meant for `cash.free2z.free2z` could open in
`cash.free2z.e2e2z`. The guard proves the patterns are pairwise disjoint.

**The trailing slash is part of the prefix.** `/bridge/zuuli/*` matches
`/bridge/zuuli/` and anything after it, and does not match a bare
`/bridge/zuuli` — which is what stops `/bridge/zuuli-evil/…` from being claimed
by ZUULI. A client must always emit the slash.

**`/oauth/callback` is listed but not claimed by any build.** ZUULI's OAuth relay
terminates in the custom scheme `cash.free2z.zuuli://oauth/callback`, and this
change does not move it. The component is carried because it is already live in
the served document and dropping it would be a regression.

## The fingerprints are Play **App Signing** keys, never upload keys

Each app is a separate Play listing with its own Play App Signing certificate,
read from **Play Console → Setup → App integrity → App signing**. There is no
single "the" fingerprint, and reusing one app's certificate for another package
is exactly the valid-but-wrong document this mechanism exists to avoid.

The distinction is the classic way this fails. The upload certificate signs the
AAB that goes to Play; **Play then re-signs** with the app signing key, and that
is what users' installs carry. An upload key verifies in a sideloaded test build
and fails for everyone else — and **Android caches a negative verification
result**, so a valid-but-wrong `200` sticks while a `503` is retried. ZUULI's
upload certificate is named as forbidden in the guard so pasting it here is a red
build.

## Where they are actually served

`https://free2z.com/.well-known/apple-app-site-association` and
`https://free2z.com/.well-known/assetlinks.json`, from the deployment
repository's nginx configuration, which serves both from exact-match locations on
the `free2z.com` server block ahead of its 301 to `free2z.cash`. Neither Apple
nor Android follows a redirect for these documents, which is why they live on
`free2z.com` and not on the canonical product host.

Two consequences that are easy to get wrong:

- **The Android route deliberately returns `503` until every listed package has a
  reviewed fingerprint.** That is correct, not a gap: a partial document is a
  cacheable "this app is not associated" answer for every app it omits, and a
  `503` is retried. So App Links cannot be switched on for one app ahead of the
  others.
- **Do not add either document to a web-served directory in this repo.** A
  `.json` file under `ts/react/free2z/public/.well-known/` is served on
  `free2z.cash`, which no app claims and which has no reviewed generator behind
  it; `apple-app-site-association` has no extension and would not be served at
  all. That combination — half an unreviewed association on the wrong host — is
  the precise failure the `503` contract exists to prevent.

## Migrating to `free2z.cash`

Recommended, and deliberately **not one change**. An association is scoped to the
exact domain: what is cached for `free2z.com` does nothing for `free2z.cash`.
The host must serve and cache both documents **first**; only then may a client
release claim it. Apple's CDN takes on the order of a day to fetch a document and
devices re-check about weekly, and Android caches a negative result — so a
`.cash`-claiming build that reaches users before `.cash` serves the association
opens a browser tab for every bridge link, for days.

Changing `ASSOCIATION_HOST` in the guard is therefore the **last** step of that
migration, never the first.
