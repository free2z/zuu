# Free2Z source inventory and workload contract

This is an initial denominator for [#1298](https://github.com/free2z/zuu/issues/1298), not a completed review or scale validation. The generated inventory records source files, not individual endpoint, model, job, route or component definitions. One file may contain many; a later scoped review must enumerate and disposition those definitions before claiming coverage. Owner `free2z` identifies the product responsible for triage, not a named operational responder. Each row carries durable triage. Initial rows are work remaining and unreviewed; hashes establish source identity only. An unchanged row retains its triage on regeneration; a changed source or classification resets it to unreviewed. Triage edits must use a valid disposition, evidence, nonempty accountable owner and, for accepted downstream work, a Free2Z issue link. A link alone is not proof of acceptance; the reviewer must verify it.

Scope is Django production Python under `py/free2z/dj` (deliberately broader than conventional views/models/tasks names), its templates, Svelte source under `ts/svelte/free2z/src`, classic React source under `ts/react/free2z/src`, and public documentation pages under `docs/about-free2z`. Tests and Django migrations are excluded, including Svelte test files. The scope manifest records owned roots and explicit asset exclusions; the generated census counts exclusions. Unknown extensions inside those roots and symlinks fail the check. New roots cannot be discovered automatically: maintainers must update the manifest when ownership or namespace registrations change. This is a conservative file inventory, not proof that all live deployments, generated pages, external services, non-Django jobs, or files with other extensions are covered. Resolve those boundaries during scoped reviews. `wallet/zuuli` readiness is a separate concern; [#396](https://github.com/free2z/zuu/issues/396) and PR #1536 are not evidence for this denominator.

Run `python3 scripts/free2z/source-inventory.py` to check the tracked inventory, or add `--write` to regenerate after inspecting source changes. It discovers tracked and non-ignored untracked files, and hashes contents, so additions, removals and modifications in scope change the result. Run `python3 -m unittest discover -s scripts/free2z -p 'test_source_inventory.py'` for classification and change-detection controls. The required zuuli static gate runs this check and its negative fixtures. Ignored files and new source roots require explicit scope decisions; no filename-based scheme can establish runtime reachability. Python AST facts enumerate recognizable URL and router registrations, model/view/task declarations; Svelte route files and component candidates are also recorded. Aliases, inheritance, dynamically constructed registrations, scheduled jobs and actual route reachability remain unresolved and require review. Facts are candidates, not a complete definition-level denominator or evidence of behavior.

Prioritize authorization and money/data correctness, then account recovery, mobile, accessibility and translation, navigation, queries/indexes, job retries/concurrency, caching, monitoring and operational ownership. Escalate concrete authorization or monetary defects immediately. The inventory itself performs no such audit. Coordinate with existing SDK work [#1047](https://github.com/free2z/zuu/issues/1047), SDK billing [#1307](https://github.com/free2z/zuu/issues/1307), and pricing/metering [#1292](https://github.com/free2z/zuu/issues/1292) and [#1291](https://github.com/free2z/zuu/issues/1291); do not duplicate their scope. Assign scoped review leaves against actual source and existing issues before creating more work.

## Workload decisions required before thresholds

No target numbers or measured capacity are established here. The accountable product owner is Free2Z; subsystem owners (Django, Svelte, classic React, and documentation) must be named by the product owner, with an operational responder assigned before capacity thresholds or alerts can be selected. Each decision below is currently unknown and needs a value, provenance, owner and review date:

- Request and concurrency mix: anonymous/authenticated traffic, reads/writes, peak and sustained load, burst shape, background work, and critical user journeys.
- Streaming: concurrent sessions, duration distribution, reconnects and provider failure behavior.
- Growth: users, content, database size, ledger entries, retention, and growth period.
- Service objectives: latency percentiles and error budgets per journey, including degraded behavior and acceptable loss or delay.
- Limits: provider quotas and rate limits, database connections/throughput, queue workers/backlog, and expected partial outages.
- Economics: cost envelope and cost per workload unit, including provider and storage costs.
- Recovery and deployment: recovery time and data-loss objectives, backup/restore, rollback, deployment concurrency and maintenance constraints.

After agreement, isolated or staging experiments must record the exact commit, configuration, workload, results, overload and provider/database/queue failure recovery. Derive thresholds, alerts and response ownership from those results. No staging or load measurement is represented by this document.
