# tauri-plugin-f2zmsg

The messaging engine behind ZUULI's end-to-end encrypted chat, exposed as the
command surface [`docs/e2ee/CLIENT-CONTRACT.md`](../../../docs/e2ee/CLIENT-CONTRACT.md)
§3 specifies. It composes the merged crates — `f2z-msg-identity`,
`f2z-msg-mls`, `f2z-msg-store`, `f2z-relay-proto`, `f2z-codec` — into something
a webview can talk to.

The TypeScript half already exists and is merged. `wallet/zuuli/src/lib/messaging/`
carries `types.ts`, `bridge.ts`, `events.ts`, `mock.ts` and a mechanical parity
test, written against the same document by a different author. This crate is
what makes its non-mock path real, and the two were built independently on
purpose — §"Disagreements found" below is what that bought.

## Run the acceptance test

```console
$ cargo test --features relay-harness
```

Two `f2zmsg-peer` processes, each with its own SQLite file and its own
CSPRNG-generated device keys, against a real `ws://` listener. They perform
`WIRE.md` §12.5's handshake — `CREATE_CONTACT_QUEUE`, `CONTACT_APPEND` behind a
proof-of-work stamp, `CREATE_QUEUE`, `SUBSCRIBE`, `BIND_SEND`, `APPEND`, `READ`,
`ACK` — and exchange a message each way as real MLS `PrivateMessage`s under
`MLS_256_XWING_CHACHA20POLY1305_SHA256_Ed25519`.

Each peer reports the `msg_id` it sent and the one it received. `msg_id` is
BLAKE2b-256 over the canonical §7 envelope and is **recomputed by the receiver**
rather than carried, so `alice.sent == bob.received` is a statement about bytes
and not about a label.

Against the standalone fake relay instead of the in-test listener:

```console
$ cd ../../../rs/deploy && docker compose -f docker-compose.dev.yml up
# → ws://127.0.0.1:9944/relay/v1
```

## The rules this crate is built around

**Never ACK before the durable local write completes** (§9 rule 1). The relay
deletes on ACK, so an ACK plus a crash is permanent message loss — not from the
relay, not from the peer, not from the mnemonic. `engine.rs`'s module header
states the exact order and names the one window that ordering cannot close.

**The `on_event` handler is not `tauri-plugin-zcash`'s** (§9 rule 6). That
plugin clears its in-memory seed on `WindowEvent::Focused(false)`. Desktop
windows lose focus constantly, and a messaging engine that tore its state down
on blur would drop relay connections and stop acknowledging inbound messages
every time the user looked at another window. `Exit` and `ExitRequested` only.

**Enrollment is not here** (§2.2). It needs the wallet seed, and routing it
through a plugin would put the mnemonic in the webview's JavaScript heap. It is
an app-crate command invoked with no `plugin:` prefix, calling
`Engine::prepare_device` and `Engine::install_identity` — neither of which sees
the seed either.

## Adding a command

1. Add the ident to `command_registry.rs`, in its §3 section.
2. Add the `#[command]` function to `src/commands.rs` and the `Engine` method
   it delegates to.
3. Add `allow-<kebab-name>` to `permissions/default.toml`.
4. `cargo build` — `build.rs` regenerates `permissions/autogenerated/` and
   `permissions/schemas/schema.json`. **Commit them.**
5. `node ../../../scripts/check-tauri-plugin-permissions.mjs`.
6. Add the row to `CLIENT-CONTRACT.md` §3 and the method to `bridge.ts`;
   `wallet/zuuli/scripts/messaging-contract.node-test.mjs` compares all three.

Steps 1, 2 and 4 are machine-enforced against each other, and since 2026-08-25
so are 3 and the capability files.

## §7 comes from `f2z-msg-dag`, and adopting it fixed a defect

`src/framing.rs` was §7 written here because the crate did not exist on any
branch when this plugin was started. It landed mid-flight (#732) and this crate
now uses it; `src/envelope.rs` is the adapter and `framing.rs` is deleted.

That was not merely deduplication. `framing.rs` linearised a conversation by the
sort key **alone**, and `f2z_msg_dag::order` documents what that costs:
applying `(epoch, senderLeafIndex, msgId)` to *every* pair — rather than only to
the pairs the causal DAG leaves incomparable — **puts replies above the messages
they answer**, in every one-to-one conversation where the replier holds the
lower leaf index. Two independent readings of the same paragraph both took the
tie-break for the whole rule, which is a good argument for one crate.

`list_messages` now pages over `MessageDag::display_order()` — Kahn's algorithm
with a min-heap on the sort key, deterministic over the graph and the keys and
nothing else.

### `msg_id` commits to `sender_leaf_index` (#734)

The second component of §7's sort key used to live only in MLS framing, and §7's
repair path delivers a message **outside** the framing it was authored in — so
two receivers who learned one message by different routes could render different
transcripts. It is a hashed field of the envelope now, cross-checked against the
framing on direct delivery (`DagError::LeafIndexMismatch`), and
`DagEntry::from_repair` takes no leaf index because there is nowhere else for one
to come from.

### Three codepoints this plugin had to allocate

`MessageType` names seven types, which is `ARCHITECTURE.md` §7's list.
`CLIENT-CONTRACT.md` needs three it does not: §3.8's ephemeral hint and §3.9's
purge request and acknowledgement. They travel inside MLS — a hint is only
meaningful because it is attributable — so they need codepoints, and
`src/envelope.rs` allocates 8, 9 and 10 pending registration upstream.

### Control payloads carry `parents` but are not DAG vertices

A vertex has to survive a restart or it manufactures gaps: this plugin persists
the transcript and rebuilds the DAG from it, so a vertex with no store record
disappears and the next message referencing it produces a dangling parent for
something nothing lost. The two-process harness found exactly that with the
in-band `queue_advert`. `envelope::is_transcript_vertex` draws the line and
states the cost: a lost advert or hint is undetectable — which for an advert
surfaces immediately as a conversation that cannot send, and for a hint is what
§3.8 already says a hint is.

## Disagreements found between the TypeScript and the contract

Two independent implementations meeting is how these surface. Neither is
silently resolved here.

**1. `set_witness_set`'s `witnesses` argument.** §3.11 declares
`WitnessInput { witnessId, name }`; `bridge.ts` types the parameter as
`witnesses: string[]` and `parity.test.ts` passes `[["0f2c8a41"], 2]`. The
document's shape carries a display name the user chose; the bridge's drops it.
`models::WitnessInput` accepts **both** encodings — a bare hex string leaves the
name empty — so neither side is broken while the question is settled. Settling
it means either adding the object form to `bridge.ts` or removing `name` from
§3.11, and the second is the smaller contract if names turn out to be
per-client rather than per-witness.

**2. There is no error envelope.** §8 says "every rejected command … carries
exactly one member", and `types.ts` declares `ErrorCodeSchema` and
`isRetryable(code)` and nothing else — no wrapper type, no shape for a rejected
`invoke`. So `error.rs` serializes the **bare kebab code**, which is the only
form the client can parse, and routes the human-readable context to `tracing`
where the webview cannot see it. `tauri-plugin-zcash` serializes `Display` prose
instead; that is right for a plugin whose client reads errors as English and
wrong here. If a future contract wants detail alongside the code, it needs a
declared envelope in `types.ts` first.

**3. ~~`compareMessages` implements the tie-break and not the order.~~ Fixed
upstream while this was in flight (#736), and the fix went further than the
report.** §5.2 used to say display order was *"recomputed by the UI, always"* —
a sentence that mandated a second implementation of a normative protocol rule in
another language, which is what ADR 0001 exists to prevent, and it duly
diverged. That sentence is withdrawn, `compareMessages` is deleted, and §9 rule
10 is now *"never order a transcript in the frontend"*.

The consequence for this plugin is a **requirement**, not a nicety:
`list_messages` returns a contiguous window of the order induced by every
message the conversation holds — not a locally sorted page — because the UI
renders the sequence as given. §7 also fixes the cursor: it is a `msgId`, never
an offset, since positions in a topological order are not stable under arrival.
Both hold here.

## What is not wired yet, and exactly why

**ZUULI does not link this plugin.** `wallet/zuuli/src-tauri` cannot, today:

```
librustzcash  bip32 = "=0.6.0-pre.1"   →  sha2 = "=0.11.0-pre.4"
messaging     ed25519-dalek 3          →  sha2 = "^0.11"          → 0.11.0
```

Cargo unifies semver-compatible versions, and `^0.11` does not match a
pre-release, so the two cannot coexist in one graph. Reproduce it by adding
`tauri-plugin-f2zmsg` to `wallet/zuuli/src-tauri/Cargo.toml` and running
`cargo check`. It is not a pin we chose: upstream librustzcash `main` still
carries the same `bip32` requirement, so a submodule bump does not fix it, and
`transparent-inputs` — which pulls `bip32` — is load-bearing for the wallet.

Consequences, all of them recorded rather than worked around:

* `capabilities/default.json` and `capabilities/mobile.json` carry no `f2zmsg:`
  entries. A capability naming a plugin the app does not link fails
  `tauri_build::build()`. `scripts/check-tauri-plugin-permissions.mjs` records
  the empty grant with this reason and refuses an empty one without a reason.
  Adding the mobile entries will also need
  `wallet/zuuli/scripts/mobile-webview-authority.mjs`'s reviewed allowlist
  extended — mobile authority is granted by review, not by registration.
* `wallet/zuuli/src-tauri/src/messaging.rs` — the enrollment trio — is written
  and not landed, because it cannot compile until the plugin links.

**The key-transparency directory has no client.** `f2z-kt` is a running server
and `f2z-kt-core` is the client verifier, but nothing carries a `/kt/v1/lookup`
between them. So `resolve_handle`, `start_conversation`,
`accept_contact_request` and self-audit fail closed with
`witness-threshold-unmet`, which is the truthful code: zero independent
witnesses have cosigned anything. §6.4's matrix and §9 rule 5 make that the
required behaviour rather than a placeholder — an unverified key at first
contact *is* the MITM. Manual safety-number verification, which §8 tells the UI
to offer instead, works in this build.

**A credential does not attest the key a peer encrypts to.** `DeviceCredential`
binds a `device_kem_pk`, and the HPKE init key MLS actually uses is the one
OpenMLS generates inside each `KeyPackage`. Neither `f2z-msg-mls` nor
`f2z-msg-identity` offers a way to bind the two — the engine needs the credential
before it exists, and the credential needs the key — so this crate supplies an
opaque placeholder, exactly as `f2z-msg-mls`'s own tests do. `KT.md` §4.1
requires only that it is non-empty. Breaking that circularity is upstream work.

**The local store is not encrypted at rest.** §6.1's `locked` is implemented as
a state machine, and the device signing key is sealed under the seed-derived
`BackupWrapKey` — so a copy of the store taken without the mnemonic cannot sign
as this identity. The SQLite database beside it is not encrypted, because
`f2z-msg-store` offers no at-rest encryption and a plugin cannot add it from
outside. MLS group state and message plaintext are protected by file
permissions and nothing else.

## Dependencies worth a second look

`f2z-relay-testkit` is a **dev-dependency and must stay one**. It is MIT and it
contains the only other relay client in the tree, but its own crate
documentation says "ZUULI's engine and the WASM web client are the clients, and
neither links this", and it carries a relay *server* with a fault injector.
`src/relay.rs` is this plugin's own client; the testkit is the relay the tests
run against.

`src/relay.rs` is also not its final home. ADR 0001 wants one Rust core shared
by ZUULI and the browser, and a client inside a Tauri plugin cannot reach
`wasm32-unknown-unknown`. Everything protocol-shaped in it is already
`f2z-relay-proto`'s and `f2z-codec`'s, so lifting it into
`rs/crates/f2z-relay-client` is a move rather than a rewrite.
