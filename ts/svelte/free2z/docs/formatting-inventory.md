# Free2Z UI formatting inventory

`tests/formatting-inventory.json` is the Free2Z UI maintainers' owned inventory and shrinking baseline. Every entry records the source file, complete normalized call, fingerprint, classification and rationale. `node scripts/check-formatting-inventory.mjs` parses Svelte component ASTs and TypeScript/JavaScript ASTs across `src/`. It checks executable `Intl` formatting, locale case conversion, `toLocale*`, `localeCompare`, ISO serialization, and `date-fns` imports; comments and type-only references are not calls. The checker is run by `npm test`, including disposable negative controls. An added or changed call fails until it is removed or explicitly classified; removing a site requires removing its stale entry. The checker caps the inventory at 105 sites and the legacy class at 51; lower the relevant caps when entries are removed. Do not regenerate the baseline wholesale.

At this revision there are 105 sites: 8 shared implementations, 10 fixed-precision sites, 10 machine/protocol sites, 26 specialized sites, and 51 legacy sites. The baseline gives the exact call for each. The legacy entries are outstanding migration work, not proof that direct formatting is centralized. Their migration must preserve each call's options, numeric precision, and the meaning of its input. In particular, billing values need their units and rounding independently verified; language-name formatters handle arbitrary content-language tags and cannot blindly use the UI-only locale normalizer.

Fixed-precision sites retain decimal strings or BigInt and obtain grouping or separators without converting the value to a float. The `en-US` plain-decimal formatter in `format-tuzis.ts` is an internal decimal conversion, not a viewer-language choice. Machine sites include stable identifier ordering and UTC serialization. Specialized entries cover tag canonicalization, grapheme boundaries, comparison case normalization, timezone discovery, and a date error fallback. Preserve their semantics when touching them.

The shared currency and unit APIs cover explicit numeric display and exact integer scales. Existing paths still need migration: currency precision differs between fixed-point ledger strings and already-numeric presentation values, while unit callers use different scaling and rounding. The next migration must define those contracts and test exact large and fractional values before replacing the existing paths. This inventory is syntactic, not whole-program dataflow analysis; references that extract an Intl constructor or object are also guarded as escape sites, but other indirect dataflow still needs review.

`formatCurrencyMajor` accepts finite major-unit numbers, bigint integers, or plain decimal strings and a supported fiat code. Numbers retain their existing floating-point value; use a string for an exact decimal. `formatCurrencyMinor` accepts a bigint and an explicit decimal scale and defaults to displaying that scale; options can select another display precision. `formatScaledAsset` formats bigint base units at an explicit scale and labels only 2Z or ZEC; it does not convert or price them. `formatLocalizedUnit` accepts a finite number or bigint and an Intl-sanctioned unit with caller-selected options. All default to the request locale and reject unsupported locales or invalid input; Intl rejects invalid units and formatting options. Exact decimal strings are refused on engines that cannot format them without double conversion. Signed decimal strings and numeric negative zero retain their sign according to Intl options; bigint has no negative zero.
