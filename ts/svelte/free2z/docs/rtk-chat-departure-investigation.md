# Free2Z stream chat after a participant leaves

Issue #1421 describes an image disappearing from chat after someone leaves. The report does not identify whether the image is a sender avatar or an attachment, nor establish the exact event sequence.

The Svelte stream's `InlineRtkMeeting` mounts `rtk-meeting`; its paginated chat uses `@cloudflare/realtimekit-ui` 2.0.3. The native Free2Z stage also embeds the provider meeting component. In the pinned paginated renderer, an incoming message's picture is looked up by `userId` in the current joined or waitlisted participants; the name comes from the message's `displayName`. An image attachment uses the message's `link` independently. The avatar component uses initials when its picture is missing or fails to load. Below 400px viewport width the SDK hides the avatar column, while the sender name remains visible.

`tests/browser/rtk-chat-departure.spec.ts` mounts the shipped paginated custom element using the same loader as the application, with an in-memory meeting and no provider connection. It emits text and image messages, removes the sender and emits `participantLeft`, checks the unchanged rendered message, then emits a message edit to force a list rerender. Distinct local image fixtures verify the attachment source and decoded width throughout. This is a component contract, not a full application meeting lifecycle test. At desktop width the image avatar becomes Alice's initial; the sender name and image attachment remain. Rejoining and rerendering restores the avatar; a broken image falls back to the initial. At 390px the avatar is hidden by the SDK's responsive styling and the sender name and attachment remain. Removing the element removes its chat listener. The paginated chat subscribes to `chatUpdate`, not participant departure; this test forces rerender with an edit and does not assert that departure itself rerenders the list.

Expected behavior is that historical messages and their attachments remain available after departure, with a sender name and an initial when a picture is unavailable. The simulation confirms this under the stated conditions; it is not a product fix and it does not prove what happened in the reported live session, test provider-hosted attachment lifetime, or establish the screenshot's image identity. A live observation with the relevant message and event sequence is still needed to explain the report. No app-side participant cache or chat replacement was introduced.
